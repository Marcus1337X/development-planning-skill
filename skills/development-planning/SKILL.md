# Development Planning

使用结构化开发计划管理软件开发。

计划保存当前有效方案；开发日志记录有意义的实际变化；`current.md` 用于跨会话恢复开发位置；`manifest.md` 用于确认哪些开发资料曾经真实创建成功。

按需读取：

- 项目列表模板：`references/projects-template.md`
- 开发资料清单模板：`references/manifest-template.md`
- 当前开发位置模板：`references/current-template.md`
- 全局规划模板：`references/global-plan-template.md`

- 开发资料清单校验脚本：`references/validate_project_manifest.py`

`references/` 中路径均相对于本 Skill 根目录。执行 Python 脚本时使用脚本的实际 Skill 路径，不得按项目工作目录猜测相对路径。

所有时间必须运行北京时间脚本获取，不得自行生成或推测。

## 文件存储

开发资料统一存放于当前开发工作区的：

`.development/`

```text
.development/
├── projects.md
└── {项目名称}/
    ├── manifest.md
    ├── current.md
    ├── global-plan.md
    └── modules/
        └── {两位补零模块序号}-{模块名称}/
            ├── implementation-plan.md
            └── development-log.md
```

`references/` 只存放 Skill 自身模板和工具，不得保存实际项目开发资料。

## 项目登记

`projects.md` 记录：

- 项目名称
- 项目根目录绝对路径
- 创建时间
- 开发资料清单路径
- 项目概述

新项目按 `references/projects-template.md` 追加。

项目创建时间必须运行北京时间脚本获取。

当前项目始终由用户决定。用户可以选择：

- 手动将 `[]：{项目名称}` 修改为 `[✅]：{项目名称}`。
- 明确授权 Agent 代为设置当前项目。

Agent 不得在没有用户明确授权的情况下自行添加、删除、移动或切换项目的 `✅` 标记。

用户明确要求 Agent 代为设置当前项目时：

1. 必须先读取 `projects.md` 并确认目标项目已登记。
2. 如果目标项目已经是唯一 `[✅]`，只需告知用户，无需重复修改。
3. 如果当前没有 `[✅]`，可将目标项目从 `[]` 修改为 `[✅]`。
4. 如果其他项目当前带有 `[✅]`，只有用户的指令明确要求将目标项目设为当前项目时，才可将原项目改回 `[]`，并将目标项目改为 `[✅]`。
5. 修改后必须再次检查 `projects.md`，确认最终只有目标项目一个 `[✅]`。
6. 代为设置仅代表执行用户已经作出的项目选择，不代表 Agent 可以自行决定当前项目。

## 项目查询与移除

用户询问已有项目、项目列表、当前有哪些项目或类似信息时：

1. 必须读取 `.development/projects.md`。
2. 将其中登记的项目内容完整列出，不得只列项目名称。
3. 完整信息包括 `[✅]` / `[]` 标记、项目名称、项目目录、创建时间、开发资料清单路径和项目概述。
4. 不得根据聊天上下文、`current.md` 或模型记忆代替读取 `projects.md`。

`projects.md` 是项目列表的唯一事实来源。

用户可以要求移除某个已登记项目。默认“移除项目”只包括：

- 删除 `.development/{项目名称}/` 及其中的 development-planning 管理资料。
- 删除 `projects.md` 中该项目对应的登记条目。

不得默认删除 `项目目录` 字段指向的真实源码项目、代码仓库或用户文件。

执行移除前必须：

1. 读取 `projects.md` 并确认目标项目存在。
2. 明确列出即将删除的 `.development` 管理目录和项目登记条目。
3. 明确显示真实项目目录绝对路径，并说明该真实源码目录不会被删除。
4. 如果目标项目带有 `[✅]`，明确提醒用户它当前被标记为当前项目。
5. 请求用户进行第二次明确确认。
6. 未获得第二次明确确认前，不得删除任何内容。

获得确认后，只删除已明确列出的 development-planning 管理资料和登记条目。

如果移除的是 `[✅]` 当前项目：

- 删除后不得自动为其他项目添加 `[✅]`。
- 提示用户如需继续其他项目，可手动设置新的 `[✅]`，也可以明确授权 Agent 代为设置。

项目移除只能由用户明确发起。不得根据项目已完成、长期未使用、路径不存在、资料缺失或 Agent 自身判断而自行移除。

如果用户明确要求删除真实源码项目目录，必须将其视为独立于“移除 development-planning 项目”的高风险文件删除请求，重新明确删除范围并单独确认；不得把项目管理移除确认视为源码删除确认。

## 开发资料清单

每个项目维护：

`manifest.md`

清单只记录项目状态目录中的开发资料相对路径。

文件尚未确认创建时：

`[]：{相对路径}`

确认文件实际创建成功后：

`[✅]：{相对路径}`

例如：

```text
[✅]：current.md
[✅]：global-plan.md
[]：modules/01-用户认证/implementation-plan.md
[]：modules/01-用户认证/development-log.md
```

`[✅]` 表示该文件曾经真实创建并确认存在，是持久历史事实。

不得因为文件后来缺失而自动删除 `✅`、改回 `[]` 或移除清单记录。

### 创建事务

首次初始化项目或新增模块资料时：

1. 先将预期文件以 `[]` 写入 `manifest.md`。
2. 按对应模板创建文件。
3. 确认文件实际存在且写入成功。
4. 再将对应 `[]` 改为 `[✅]`。

不得在文件尚未成功创建前提前标记 `[✅]`。

如果 `[]` 对应文件已经存在，应先检查文件内容和用途；确认属于本 Skill 正确创建的目标文件后，才可改为 `[✅]`。

### 首次初始化完成提醒

首次初始化项目完成后：

1. 不得自行给新项目添加 `[✅]`。
2. 必须向用户输出以下提示，并同时提供“手动设置”和“授权 Agent 代为设置”两种选择。
3. 必须存在唯一 `[✅]` 当前项目后，才能开始正式开发。
4. 在用户完成手动标记或明确授权 Agent 代为标记前，不得将该项目视为当前开发项目，也不得开始实现功能。
5. 不得因为该项目刚完成初始化就默认它是当前项目。

固定提示：

```text
项目开发资料已初始化完成。

开始开发前，必须先明确选择当前开发项目。你可以选择以下任一种方式：

方式一：手动设置

请打开工作目录下的：

.development/projects.md

并手动将：

[]：{项目名称}

修改为：

[✅]：{项目名称}

方式二：由我代为设置

你可以直接告诉我：

帮我将「{项目名称}」设为当前项目。

收到你的明确授权后，我可以代为修改 `projects.md`，并确保最终只有该项目一个 `[✅]`。

只有存在唯一的 `[✅]` 当前项目后，Agent 才能开始或恢复开发。

这样做的目的是由你明确决定当前正在开发哪个项目，避免 Agent 自动选择错误项目、跨项目读取或修改文件，并确保开启新会话后能够恢复到正确的项目和开发位置。

无论采用哪种方式，当前项目都由你决定；Agent 不会自行选择或切换项目。
```

## 缺失保护与补建

开始开发或恢复新会话时，必须运行开发资料清单校验脚本。

如果 `manifest.md` 中某个 `[✅]` 文件当前不存在：

1. 视为“曾确认创建但当前缺失”。
2. 停止依赖该文件的后续开发。
3. 明确告知用户缺失文件路径。
4. 告知用户该文件曾被 `manifest.md` 确认创建过，因此不是简单的“尚未创建”。
5. 告知用户可以让 Agent 补建该文件。
6. 未经用户明确同意，不得自动重建。

推荐提示：

`检测到 {文件路径} 曾经确认创建，但当前已经不存在。该文件可能被删除、移动或丢失。为避免覆盖未知历史内容，我不会自动重建。如果你需要，我可以根据当前项目资料和对应模板为你补建该文件。`

用户明确同意补建后：

- 先说明无法保证恢复已经丢失的历史内容。
- 根据当前代码、现存计划、日志及对应模板尽可能重建。
- 确认补建文件实际存在。
- 保留原 `[✅]` 清单记录，不登记为首次创建。

`[]` 对应文件不存在表示尚未确认创建，不视为文件丢失。

## 项目边界

开始开发或恢复新会话前，必须运行项目边界校验脚本。只有返回 `VALID` 才能继续。

校验失败时：

- 立即停止开发操作
- 不得自行切换项目或工作目录
- 不得修改项目的 `✅` 标记
- 不得读取、修改或操作其他项目目录
- 根据脚本返回原因引导用户处理

允许开启新对话会话；新会话必须重新校验。

当前项目根目录是本次开发的文件系统边界。除本 Skill 自身资源外，不得主动跨项目目录。

## Agent 项目指令

每个项目应配置当前 Agent 或宿主开发环境官方支持的项目级持久指令，用于在新会话中提醒 Agent 使用本 Skill。

已知示例：

- Codex：`AGENTS.md`
- Claude Code：`CLAUDE.md`

对于其他 Agent：

1. 优先识别当前宿主环境提供的项目指令机制。
2. 无法确定时，可查询当前 Agent 帮助、本地文档、官方文档或可用检索能力。
3. 只使用能够确认由当前 Agent 官方支持的名称、目录和格式。
4. 不得根据其他 Agent 的规则猜测名称或扩展名。
5. 无法可靠确认时，不创建未知文件并提示用户。

确认机制后：

- 只在当前项目根目录范围内处理对应指令文件。
- 文件不存在时，可按官方机制创建。
- 文件已存在时，不得覆盖、删除、重排或改写用户已有内容。
- 若不存在 development-planning 区块，在合适空白位置追加 `references/agent-instruction-block.md`。
- 已存在该区块时不得重复添加。
- 仅维护 `<!-- development-planning:start -->` 与 `<!-- development-planning:end -->` 之间内容。

项目指令只作为本 Skill 入口，不复制完整 `SKILL.md`。

## 当前开发位置

每个项目维护 `current.md`，由 Agent 自动维护。

它只记录恢复开发所需的状态指针，不复制计划、验收标准或开发日志。

固定字段：

- `当前项目`
- `项目开发状态`
- `当前模块`
- `当前模块开发状态`
- `当前功能`
- `最后更新时间`

项目开发状态与当前模块开发状态只使用：

- `从未开始`
- `正在开发`
- `开发完成`

初始状态：

- `项目开发状态：从未开始`
- `当前模块：尚未正式开始开发`
- `当前模块开发状态：从未开始`
- `当前功能：尚未正式开始开发`

状态含义：

- `从未开始`：尚未实际进入对应项目或模块的功能实现。
- `正在开发`：已开始实际实现，但尚未全部完成。
- `开发完成`：对应项目或模块的计划功能均已完成并通过必要验证。

状态更新规则：

- 首次实际开始某个模块的功能实现时，将项目开发状态更新为 `正在开发`，当前模块开发状态更新为 `正在开发`，并记录当前模块与当前功能。
- 切换功能或模块时，更新当前模块、当前模块开发状态与当前功能。
- 当前模块全部功能完成并通过验收后，将当前模块开发状态更新为 `开发完成`。
- 项目全部模块和功能完成并通过必要验证后，将项目开发状态更新为 `开发完成`。
- 已标记 `开发完成` 的项目或模块出现新的未完成开发工作时，恢复为 `正在开发`。
- 更新 `current.md` 时必须运行北京时间脚本刷新最后更新时间。

`current.md` 中的 `当前项目` 必须与 `projects.md` 唯一 `[✅]` 项目一致。若不一致，停止恢复或开发，不得自行修改任一方，并提示用户确认。

新会话恢复顺序：

1. 运行项目边界校验。
2. 读取 `projects.md` 确认唯一 `[✅]` 当前项目。
3. 检查并读取当前项目 `manifest.md`。
4. 运行开发资料清单校验。
5. 若存在 `[✅]` 文件缺失，停止并按缺失保护规则提示用户。
6. 读取 `current.md`，校验其中的当前项目与 `[✅]` 项目一致。
7. 根据项目开发状态、当前模块开发状态、当前模块和当前功能恢复开发位置。
8. 若当前模块已进入开发，读取对应 `implementation-plan.md`。
9. 检查当前代码和实际状态后继续。

## 全局规划

创建开发计划时读取 `references/global-plan-template.md`。

将开发目标拆分为模块和功能。模块实现顺序：

- `P0`：关键基础
- `P1`：主要能力
- `P2`：增强能力

模块和功能序号统一使用两位补零：`01`、`02`、`03`……

所有模块和功能初始状态：

`**开发状态：** 未完成`

全局规划负责说明“要开发什么”。

## 模块实现计划

准备开发模块前读取 `references/module-plan-template.md`。

模块及功能序号、名称必须与全局规划一致。

模块实现文档初始版本：`0.1`。创建时运行北京时间脚本记录最后修改时间。

功能不单独维护计划版本。

## 开发执行

按：

`模块 → 功能 → 实现 → 验证 → 更新状态 → 下一功能`

开始实际开发功能前先更新 `current.md` 的项目、模块、功能与对应开发状态。

实际开发不要求机械遵循原计划。用户最新要求、当前代码、实际运行和验证结果高于旧计划。

发现原计划与实际不符时，更新当前有效计划，并按需追加开发日志。

## 开发状态

只使用：

`**开发状态：** 未完成`

和：

`**开发状态：** 已完成-结束时间-{北京时间}`

功能只有在实现完成、通过对应验收标准且不存在已知关键未完成项后才能标记为已完成。

完成时运行北京时间脚本，并同步更新全局规划与模块实现文档中的功能状态。

模块只有在所有功能均已完成后才能标记为已完成，并单独运行北京时间脚本获取模块结束时间。

开发状态变化不增加计划版本。

## 计划版本与开发日志

模块实现文档初始版本为 `0.1`。每发生一次实质性计划调整，模块版本增加 `0.1`，例如：`0.1 → 0.2 → 0.3`。

实质性调整包括：

- 新增或删除功能
- 核心实现方案或关键业务流程变化
- 异常处理规则或验收标准变化
- 用户需求变化
- 新发现的边界条件导致方案变化

发生实质性调整时：

1. 更新模块实现计划。
2. 模块版本增加 `0.1`。
3. 运行北京时间脚本更新最后修改时间。
4. 按模块开发日志模板追加开发日志。

开发状态变化、格式调整、错别字修正和无实质影响的措辞修改不增加版本，也不写开发日志。

开发日志只追加历史记录，不覆盖已有记录。

## 核心原则

`理解 → 规划 → 实现 → 验证 → 更新状态`

信息优先级：

`用户最新要求 > 当前代码和实际运行结果 > 当前有效开发计划 > 开发日志 > 模型自身推断`

- `projects.md`：用户决定当前开发哪个项目，并记录项目登记信息。
- `manifest.md`：Agent 记录哪些开发资料曾确认创建。
- `current.md`：Agent 记录当前项目、项目开发状态、当前模块、当前模块开发状态和当前功能。
- `global-plan.md`：项目整体要做什么。
- `implementation-plan.md`：模块当前准备怎么实现。
- `development-log.md`：实际开发为什么发生变化。

代码和实际验证结果始终是最终事实。
